# W2-09: attempt commit and registration vocabulary below the provider

Packet brief: `packets.md` §W2-09. Design reference: `contracts.md` family B, direction check
(flipped by the host order). Base: `e200ba0e00`. No cargo was run; the integrator compiles.

## Order that governs

Canonical host order for the primary graph (`vocabulary_simulation.host_order`, draft stack for
ties), bottom to top, for the modules this packet touches:
`provider` (47) < `application_checkpoint` (49) < `output_lineage` (55) <
`invariant_projection` (56) < `application_output_demand` (57) < `application_attempt` (60).
`vocabulary` is the bottom layer by construction: it must name no family above it.

So every reference from `provider`, `output_lineage` or `application_output_demand` to an
attempt item is upward. An item they name has to sit at or below the lowest of them that names
it, and everything that item names has to sit at or below it too.

### Why the receipt cannot move in this packet

The receipt's fields hold `provider::WorthQueryPrimaryMutationWorkEvidence`, which is sealed
authority held back in wave 1 (its seal stays in the provider). They also hold
`provider::OwnEffectOnReads`, `application_checkpoint::FactPayload`, and the attempt-owned
`WorthQueryApplicationCommitAuthorityBinding`, `WorthQueryApplicationCommitTerminalEvidence`,
`WorthQueryMutationPreconditionComparisonEvidence`,
`WorthQueryExternalDispatchPreparationDenial` and `OutputFieldCaptureFailure`. Output demand
stores receipts by value and returns `&WorthQueryApplicationCommitReceipt` from public methods,
so a read port cannot stand in for them.

The receipt therefore cannot sit below the provider. Its lowest honest place is between
`application_checkpoint` (49) and `output_lineage` (55), in a module the attempt owns. No such
module exists. A new primary-graph child needs a place in the stack file, and the attempt types
listed above would have to go down with it, each split into data and behaviour. That is an owner
call (new module plus stack ruling), not a move this packet can decide. Splitting data from
behaviour, as step 3 asks, does not help, because the blocking names are in the fields, not the
impls.

### Why `WorthQueryApplicationUncommitted` cannot move in this packet

It is a real data cycle with output demand:
`Uncommitted` ⊃ `WorthQueryApplicationCommitDeferred` ⊃ `WorthQueryOutputDemandDenial` ⊃
`cleanup_custody::DemandCleanupCustody` ⊃ (boxed) `Uncommitted`.
Its other variants carry `WorthQueryApplicationCommitDenial`, whose impls name the provider,
`application_invariant`, the attempt denial and `StoreDenial`. The cut belongs in output
demand's cleanup custody, which already erases its owner behind `dyn CleanupOwner`. The trait's
`outcome()` and `into_required()` signatures would have to stop naming the attempt's outcome
and cleanup types, with the native owner implementation moving up into the attempt. That is a
port redesign of output demand's custody (a family D–like step), outside this packet's files.

## Follow-up: no inherent impls on lowered types from the attempt

Every inherent impl of a type this packet lowered now sits in that type's own module tree. A
scan over the library for `impl <lowered type> {` outside the type's own tree finds none.

| behaviour | before | now |
|---|---|---|
| `affects_output_records` | attempt `commit_receipt::committed_output_effect` | `vocabulary::application_attempt::committed_changes::output_effect`, a child of the type's own module. It names only vocabulary, and its caller is output demand (below the attempt), so an attempt trait would have forced output demand to import the attempt. |
| `field_effect` | inherent, attempt | `CommittedFieldEffect` (attempt, `commit_receipt::committed_field_effect`), implemented there for `WorthQueryApplicationCommittedChanges`. |
| `materialize_field` | inherent, attempt | `CommittedFieldMaterialization` (attempt, `commit_receipt::materialized_committed_field`), re-exported beside `MaterializedCommittedField`. |
| `from_checkpoint_roles` | inherent, attempt | `OutputCorrespondenceRestoration` (attempt, `effect_program::output_correspondence_checkpoint`), with `Sized` and an associated constructor. |
| door `field_effect_for_test` | inherent, attempt door file | door trait `CommittedFieldEffectDoorsOps`, in the same module's door file. |
| door `from_checkpoint_roles_for_test` | inherent, attempt door file | door trait `OutputCorrespondenceRestorationDoorsOps`, in the same module's door file. |
| doors `workflow_actor_fields_for_test`, `retain_workflow_actor_evidence_for_test`, `workflow_actor_omission_for_test` | inherent on the committed changes, attempt | inherent on `WorthQueryApplicationCommitReceipt`, in `commit_receipt::committed_actor_observation`, inside the receipt's own tree. |

Why the actor-observation doors went onto the receipt rather than into a door trait: their only
callers are in `worth-query-court-decl-host-package-archive-replay-workflow-approval`. That is
a certification court outside the set `src_court_doors.py items` scans (only `*execution*`
courts and testkits), and it reaches these doors only as methods on a facade type. A door trait
would have no stable path for that court to import, and adding one to the consumer facade is
not allowed. Every call already went through `receipt.committed_changes()`, so the doors now sit
on the receipt, which owns those committed changes. `retain_workflow_actor_evidence_for_test`
drops its `receipt` argument. The receipt owns the artifact, so the check that the envelopes
matched is now true by construction. When the later design pass lowers the receipt, these doors
go with its behaviour.

Object safety: no trait is used as `dyn`, so none is made object-safe.
`OutputCorrespondenceRestoration` and its door trait are `Sized` and generic in their arguments.
The door traits have no supertrait: each is implemented for the concrete lowered type and calls
the production trait through `<Self as Trait>::`, so a `pub` door trait never names a restricted
trait. Production traits are `pub(in crate::domain_computation::primary_graph)`. Door traits are
`pub`, inside `pub(crate) mod court_doors_for_test`, as in the repo's existing `*DoorsOps`
doors.

Call sites: `scripts/query_split/extension_trait_imports.py` (committed), run with
`packet-notes/W2-09-extension-traits.json`. It added the production trait imports in 5 library
files (`causal_inspection` overlap ×3 and rich source, `application_contribution` producer
checkpoint registry; all above the attempt, so the imports point downward). It added the door
trait imports in 16 execution court files, through the door path. It reshaped 11 door calls in
the certification court (`receipt.committed_changes().workflow_actor_*_for_test(..)` becomes
`receipt.workflow_actor_*_for_test(..)`; the retain door is called on `performed.receipt()`).
`src_court_doors.py items` then regenerated 823 doors and opened the door modules to
`pub(crate)`. No door file is orphaned.

The registration request (`WorthQueryApplicationAttemptRegistration`) moved into the provider,
as its registration operation's own input: `registered_attempt::registration_request`. Its fields
are `pub(super)`, so only `registered_attempt`, where the operation takes it apart, can read
them. The attempt builds it with `WorthQueryApplicationAttemptRegistration::new(..)`. The
constructor takes the attempt's `WorthQueryProviderEffectRegistrationSeal`, whose mint stays
private to the attempt, so only the effect owner can build a request. The two
observation-retention booleans travel as a named `WorthQueryRetainedSuccessorObservations`
rather than as positional booleans. `provider_binding` re-exports the seal, no longer the
request.

The nine `effect_accumulator` readers at `pub(in crate::domain_computation::primary_graph)`:
their callers are `provider::application_attempt_state::registration::registered_attempt`
(the provider's registration operation and the record's accessors) and
`application_attempt::provider_binding`. The narrowest common ancestor of the two is
`primary_graph`, so this is the narrowest visibility that compiles.
