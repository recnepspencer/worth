# W2-04 — Computation retention family (family A): packet notes

Design: `contracts.md` Family A. Edited without compiling; the integrator's combined pass compiles.
Base `e200ba0e00` (the wave-2 branch head; this worktree started at `21de236406`, a strict
ancestor, and was fast-forwarded first).

## Which order was measured

The canonical layering is the host-supertrait order, with the draft stack breaking ties.
`vocabulary_simulation.host_order` ranks a module missing from the stack last, and
`runtime_host` (the root every host trait extends) is missing from
`ownership/stack-primary_graph.json`. Run as committed, every hosted module waits for
`runtime_host`, so `invariant_projection` (which has no host trait) lands below `provider`,
`application_checkpoint` and `output_lineage`. That is not a tie the stack decided; it is the
missing rank. With `runtime_host` ranked first, the order reproduces every direction in
`after-wave-1/primary_graph/host-order-seams.md` (`provider` < `output_lineage` <
`invariant_projection` < `application_output_demand` < `application_attempt` <
`application_contribution`), so these notes measure that way:

```text
vocabulary_simulation.host_order with stack = ['runtime_host'] + stack-primary_graph.json,
--exclude-designed seams/contracts.md seams/merges.md seams/proposal-03-plan.md
```

The exclusions reproduce the after-wave-1 counts of the four seams exactly (23/9, 16/11, 12/5,
11/7). The integrator may want `runtime_host` added to the bottom of the stack file; this packet
does not make that ruling.

`computation_retention` is entered in the stack just below `output_lineage` (its lowest consumer
under this order). It names no primary-graph module, so it sits below every consumer.

## Not done: the retention envelope cannot be lowered under the canonical order

Steps 1 (the envelope part), 3 (`CompletedComputationRetention` moving) and 5 (carried custody)
were not executed. `RetainedComputation`, `SealedComputationRun`, `SealedComputationRetention`,
`CompletedComputationRetention` with `CompletedComputationRun`, `ComputationDeposit` and the
carried custody stay in `incremental`. The design placed the new module "below
`application_attempt`, its lowest consumer". Under the host order, the consumers
`output_lineage` and `invariant_projection` sit below the attempt, yet the envelope contains data
the attempt and `invariant_projection` own:

- `RetainedComputation.facts: SealedComputationFacts` holds the attempt's `ComputationFactIndex`,
  `SealedComputationFact`/`ComputationFactReaders`, `SealedReadLayout`/`CheckedReadLayout` and
  `FactContent`. Its impls are spread over `computation_routing/{sealed,layout,reattribution,test_mutation}.rs`
  and use attempt internals (`StorageControl`, `StoreDenial`).
- `RetainedComputation.checked_calls: CheckedCallShape` holds `invariant_projection::CallShape`
  and the attempt's `CheckedReadLayout`.
- `CompletedComputationRun.call_sequence` is `invariant_projection::ComputationCallSequence`
  (read only through `shape()`), and carried custody holds `RetainedCall` →
  `invariant_projection::ComputationCallCharge` and the attempt's `NativeCallCarriage`.

`output_lineage` stores `Arc<RetainedComputation>` and `invariant_projection` holds
`ComputationDeposit`/`CompletedComputationRetention`. So wherever one module puts the envelope,
some edge points up:

| placement | upward edges created |
|---|---|
| below `output_lineage` (all consumers above) | `computation_retention -> application_attempt`, `computation_retention -> invariant_projection` |
| just below `application_attempt` (designed wording) | `output_lineage`, `invariant_projection`, `application_output_demand -> computation_retention` |
| between `invariant_projection` and `application_output_demand` | `computation_retention -> application_attempt`; `output_lineage`, `invariant_projection -> computation_retention` |

Each breaks "no new upward edge". Lowering the envelope needs two blockers removed first:

1. the attempt's sealed-facts data below `output_lineage`: W2-08 lowers the fact key and
   `CompletedFactProjection`, but not `SealedComputationFacts`, its index, layouts and
   `FactContent`;
2. `invariant_projection`'s call-shape vocabulary (`CallShape`, `ComputationCallSequence`,
   `ComputationCallCharge`) below `output_lineage`.

With both lowered, the envelope moves into `computation_retention` as designed (the same file
set), with carried custody beside `CompletedComputationRun` (step 5, recommended). This needs a
design ruling, since it touches files outside this packet.
