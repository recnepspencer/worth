## 1. Purpose

This is the one implementation reference for cleaning up and honestly finishing
Runtime Phase 8. It answers four questions without requiring another
architectural excavation:

1. What the current implementation genuinely establishes and must preserve.
2. What exists in code but is not accepted as settled product design.
3. What defects had to close before Phase 8 could honestly finish.
4. In what order those defects must be corrected and proved.

The old correction plan became unsuitable because it mixed audit history,
implementation instructions, and completion claims. In particular, it treated
the implemented undo and redo lane as settled architecture even though the
product decision is to reconsider that lane in a separate milestone.

This plan does **not** require a hard deletion of the undo and redo code. It
requires honest containment: that code may remain and must continue to compile,
but it may not close this plan, expand the public contract, introduce a second
history authority, or constrain the later milestone's design.

## 3. Product Decision Lock

### 3.1 Phase 8's accepted finish

Phase 8 finishes the following product foundation:

- an application operation owns one compiled aftermath contract;
- one schema-declared typed external emission is bound to that contract;
- the exact bounded wire projection is co-committed with the ordinary mutation;
- a real external owner receives and independently decodes that projection;
- dispatch posture is derived from distinct, predecessor-linked causal events;
- recovery handles carry owner-derived binding and fresh runtime authority;
- exact pre-mutation truth demanded by an installed contract is retained or the
  commit fails closed;
- Relational remains the only canonical commit-history and entity-lineage
  authority;
- publication exposes only sealed runtime results and cannot manufacture a
  recovery, dispatch, or history decision;
- ordinary operations with no aftermath work retain their zero-work posture.

### 3.2 Undo and redo are provisional, not deleted

The current undo and redo implementation is classified **PROVISIONAL**.

That means:

- its files, tests, and types may remain in the tree;
- compatibility edits needed to keep the workspace compiling are allowed;
- defects that let it bypass Relational, runtime ownership, or supported-feature
  authority must still be fixed;
- it is not acceptance evidence for this plan;
- no new public promise, facade dependency, feature document, or roadmap claim
  may present it as settled;
- no current cleanup slice may deepen its semantics merely because the current
  implementation already chose a shape;
- [Milestone 9.18](./milestone-9.18.md) decides
  whether to keep, revise, or remove it.

The later milestone must re-decide at least: eligible operations, inverse versus
compensation semantics, exact occurrence-level causal meaning, current-head
policy, divergence behavior, redo invalidation, idempotency, retained-input
requirements, authorization re-entry, public DX, and interaction with the
cross-runtime branching roadmap.

Two pieces remain useful outside that unsettled product decision:

- `ExpectedBranchHead` is a general Relational compare-and-commit precondition
  when it is owned and checked by Relational; its use by current redo policy is
  provisional.
- commit-time pre-image retention is a general aftermath foundation. Capturing
  exact prior truth may close here; claiming that undo restores it correctly

Milestone 9.17 owns the successor cut from Relational-only product history to

## 5. Authority Model

### 5.1 Placement decision tree

For every new or moved type, ask in order; the first `yes` wins:

1. Does it decide whether an operation is legal? Put the generic law in
   `worth-proof`, with a concrete Query owner facade where the operation occurs.
2. Would it mean the same thing crossing a boundary into another runtime? Put
   only that portable description in `worth-foundational`.
3. Does it need a clock, counter, live table, provider transaction, or `Drop`?
   Put it in the owning runtime.

Before concluding that vocabulary is absent, verify the prospective owner's
manifest can see the crate that already owns it.

### 5.2 Locked owners

| Meaning | Sole authority owner | What other layers may do |
|---|---|---|
| Declared operation, effect, payload wire identity, and aftermath meaning | Query declaration | Installation validates and compiles it. |
| Installed legal next-action contract | Query installation | Execution consumes it; hosts cannot rebuild it. |
| Generic proof, linearity, freshness-state, and boundary-readmission laws | `worth-proof` | Query wraps them in concrete owner types and supplies runtime evidence. |
| Live recovery registry, clock sampling, cleanup, and force termination | Query execution runtime | Tests observe through owner-controlled fixture APIs, not public registry capability. |
| Authoritative commit identity, ordered parents, branch head, ancestry, serialization, and publication | Relational | Query may co-commit admitted application-semantic facts but may not mirror history. |
| Authoritative entity lineage and truth correspondence | Relational | Query consumes typed owner evidence; it does not create another lineage vocabulary. |
| External effect result | External owner/rail | Query classifies only the returned observation and cannot infer completion from silence. |
| Portable description of an already-completed event or continuity fact | Foundational | It carries no current legality, head, or live owner authority. |
| Cross-runtime projection, mapping, and transport | Runtime Bridge | It cannot decide legality, currentness, parentage, or history. |
| Consumer-facing aftermath posture and disclosed next actions | Query publication | It projects sealed owner results; it mints no execution authority. |

### 5.3 Lineage and causality lock

The word "lineage" must not blur four different meanings:

- **canonical commit history** belongs to Relational;
- **canonical entity lineage** belongs to Relational;
- **operation-semantic admission** may belong to Query when a separately
  accepted product says one operation lawfully relates to another;
- **portable boundary description** may belong to Foundational only after an
  owning runtime has established the completed fact.

Runtime Bridge is never the missing authority. It may transport an admitted
projection when a real cross-runtime consumer exists. It may not create the
relation, choose a parent, decide the current head, or publish canonical
history.

The current provisional `undo-of` and `redo-of` facts are therefore neither a
Query lineage store nor Foundational history. Their product meaning remains for
the successor milestone to accept or revise.

## 6. Enforcement Standard

Every guarantee names the strongest honest enforcement rung:

| Rung | Enforcement | Use in this plan |
|---|---|---|
| **1** | Invalid state or call is unrepresentable. | Delete redundant parameters; move authority by value; separate phase types. |
| **2** | Value is unconstructable outside its owner. | Private fields/minting; sealed owner continuations. |
| **3** | Dynamic owner truth is checked at runtime. | Wire bytes, live clock, exact record/field mutation, external response. |
| **4** | Documentation only. | Never sufficient for a legality or authority claim. |

Dynamic values cannot all become distinct Rust types. Compile-time strength
means the compiler requires the owner-minted evidence or continuation that
contains those values; it does not mean replacing a necessary dynamic owner
comparison with `PhantomData` and calling it exact.

Specific rules:

- A supported feature must not make an authority-bearing item public.
- A test hook may inject data or observe an owner result; it may not grant a
  production capability that normal code lacks.
- A stable protocol family and its exact produced version are explicit declared
  protocol data, not `type_name::<T>()`; consumer support windows remain owned
  by the external consumer.
- A proof of a dynamic comparison may not be reusable for unrelated values of
  the same Rust type.
- If a later operation requires the result of an earlier one, progression must
  consume a private phase-specific value, not a bag of repeated fields.
- A runtime check is accepted only when the owner truth is necessarily dynamic
  and the checked values cannot be supplied through a second door.

## 7. Adversarial Courtroom

The courtroom is defined before the implementation slices. No slice closes by
adding only a happy-path unit test.

### Case A: supported-feature authority

Build a real external consumer with every supported feature enabled. Give it
two live handles A and B. It may observe fixture-safe posture for A, but it
cannot obtain the registry, name B's slot through A, force-terminate either
handle, choose a terminal kind, or enumerate live resources. The compile
boundary must hold under default and every supported feature set. The legacy
`test-support` authority feature must not exist or be reintroduced.

### Case B: ambiguous declaration

Author one operation with two different external-effect contracts, and another
with two different aftermath contracts. Both declarations fail before
canonical identity and installation. The positive twins with exactly one
member install and preserve deterministic identity.

### Case C: exact dynamic binding

Compare binding pair A successfully, then try to use the resulting artifact to
open pair B of the same axes type. The public surface makes that substitution
impossible or the owner continuation rejects it without accepting another
target parameter. A drift twin identifies the exact semantic axis.

### Case D: real committed outbox

Execute the Bank death-notification operation through the ordinary public
front door. After commit, obtain a fresh provider/Relational owner view and read
the outbox row. Independently assert effect identifier, version-free protocol
family, exact produced version, declared maximum, exact bytes, correlation,
outcome identity, and commit affinity. Mutating or omitting any one field must
fail the oracle.

### Case E: real external meaning

Send the committed outbox payload through the separate rail process. The rail's
independent decoder must ledger the exact estate, notice, and subject. Then run
hostile twins for wrong effect, wrong protocol family, predating/retired/future
version, crossed-version or malformed bytes, and dishonest bound. Each is
rejected before ledger admission; healthy v1 and v2 twins complete.

### Case F: causal predecessor ladder

For one dispatch, assert four distinct identities:

```text
Relational provider commit
    -> admitted/co-committed application emission
        -> dispatch attempt
            -> external-owner observation
```

Every edge names its exact predecessor. Lost response, acknowledgement without
completion, duplicate acknowledgement, timeout followed by completion, and
safe retry must not let an earlier identity construct or impersonate a later
posture.

### Case G: exact retained field

Read two fields on one record, mutate only field B, and demand prior truth for
field A. The commit denies. The positive twin mutates the exact demanded field
and retains its pre-mutation value. Repeat with two records sharing the same
slot to preserve the existing wrong-record protection.

### Case H: publication ownership and noninterference

Create publication only from a sealed committed/runtime outcome. An external
consumer cannot construct it from raw receipt fields, a wire identity, a
recovery slot, or a copied posture enum. A protected fact may influence an
internal aftermath decision without leaking through explanation, next-action
availability, causal shape, or identifiers. Runtime Bridge is absent from the
legality path.

### Case I: provisional-lane containment

Mechanical residue and dependency checks prove the provisional undo/redo lane
owns no chain, mutable head, parent selection, canonical publication, Bridge
authority, or Foundational upgrade. Public docs call it provisional. Its tests
remain regression tests, not exit evidence.

### Case J: ordinary-lane noninterference

With a live transport installed, commit an operation declaring neither external
effect nor recovery work. It creates no outbox row, performs no dispatch, mints
no handle, and records zero work in every Phase 8-specific counter.
