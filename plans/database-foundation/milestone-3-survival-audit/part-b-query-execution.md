## 4. Spec conflicts and underspecified seams

These are findings for the coordinator, not amendments to the specification.

1. **Outbox identity wording is factually wrong at this HEAD.** Phase 1/8's
   example places `relational_runtime_instance_id` in an outbox row; §2 shows
   it is an observation-only field. Real durable identity work also includes
   transport causal digests, workflow receipt digests and runtime source
   commitments. Removing only a supposed raw outbox column would miss those.
2. **Required-output obligations need a named durable placement and phase.**
   Phase 6 promises preservation of required-output execution/failure semantics;
   Phase 9 explicitly names correction pending-publication entries. The
   `DemandRecord` performed obligations/prerequisites and `SourceCustody` are
   neither all derived nor all covered by saving Ready outputs. The closed
   journal registry names support/adoption/managed/conditional/owned-async for
   `query.obligations`, but does not explicitly place general required-output
   custody. The table assigns its earliest requirement to 6 and managed work
   to 7; the governing format/refusal mapping must explicitly cover it before
   Phase 6 promises can hold. Evidence: `P/application_output_demand/registry.rs:248`.
3. **Conditional state topology is wider than Phase 7's four retained names.**
   `P/conditional_operation/signal_decision_reentry/retained_decision.rs:3`
   also includes ExecutionControlRetryable, Backpressured, ControlStopped,
   TerminalFailure, ProductUnpublished, Indeterminate, Failed and
   InterruptedDuringReentry. Some carry the already listed mandatory custody;
   others can be re-derived or are terminal. The phase must explicitly state
   each recovery/terminal disposition instead of silently dropping every
   non-listed variant. This audit does not choose new lifecycle semantics.
4. **“Coverage” has two owners.** Phase 7's graph-record coverage requirement
   matches proposal coverage (`P/workflow/schema/proposal_coverage.rs:14`).
   Installed vocabulary coverage is a typed installation vector
   (`P/workflow/adoption/coverage.rs:14`) recreated from the supplied program.
   The specification should distinguish them; persisting an installed
   interpreter/registration as authored approval coverage would be incorrect.
5. **Retention classes require contract-specific encoding.** Phase 9/D10 say
   each correction artifact is optional or an obligation according to its
   contract. The current pre-image/input/disclosure carriers have no durable
   class envelope. Prepared correction pins preserve optional material while
   in use (`P/product_operation/correction_source/preparation.rs:20`), and
   recovery bindings can hold the same kinds of material. The phase must
   declare the class for each retained use and transfer/pinning rule; treating
   every receipt sidecar as optional would violate mandatory recovery. Table
   rows name the optional source material separately from mandatory custody.
6. **Run recovery needs data contracts for opaque process objects.**
   `E/managed_run/retained_graph_execution.rs:16` retains a provider checkpoint,
   memory arena and artifact context; `P/application_attempt/commit_authority_binding.rs:23`
   retains `Arc<dyn Any>`. Phase 7/9's resume goals cannot be implemented by
   serializing these values. Owner-defined versioned data/readmission contracts
   and the exact existing terminal alternative for each run kind need to be
   specified. No evidence here establishes that all such kinds already have
   cross-process checkpoint codecs.
7. **Branch cleanup crosses phase gates.**
   `P/product_operation/cleanup.rs:21` combines native World cleanup and
   conditional assembly cleanup. Phase 4 custody release, Phase 5 Signal
   support and Phase 7 managed/conditional cleanup must classify the actual
   components before admitting the creating operation. A blanket claim that
   every cleanup is supported in Phase 4, or every cleanup may wait until 7,
   leaves a gap; D15's capability mapping must distinguish the component set.
8. **Inbound source controls are currently runtime-scoped.**
   `P/application_runtime/inbound_occurrence.rs:48` says so explicitly, and
   installing a verifier initializes its posture to Active at `:145` after
   retirement/revocation at `:65`/`:71`. Phase 8 names durable inbound custody
   but does not decide whether source revocation itself is a home-level fact
   or fresh host configuration. The process-local classification above follows
   today's stated contract; it does not claim that resetting a home-level
   revocation would be safe.
