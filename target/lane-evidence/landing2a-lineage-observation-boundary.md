# Exact lineage observations: unresolved public boundary

Reviewed paths: lineage/access/{mod,records,resolution,selected_root_resolution}.rs;
change_source/lineage_at_observation.rs; facade.rs::lineage; cold lineage event/node
courts and their reviewed per-test map. Existing record_history_at_observation
first demands Full and resolves selected-root-reachable ancestry. Raw private
resolve_historical_lineage uses the authoring-branch event corpus. Those are
not equivalent footprints or ancestry meanings; swapping them is insufficient.

Candidate minimal signature (not implemented or approved):
`read_lineage_history(request, branch: &RelationalBranchIdentity, seed: LineageId)`.
The branch identity proves runtime/branch ownership; it does not freeze a corpus
cut. Calling observe_branch then discarding its selected basis before using the
raw authoring-branch resolver might expose an incoherent read while publication
progresses. Restricting the resolver to the observation changes the original
branch-corpus claim. Need verify whether an existing original event-page lease
already carries the required cut, and whether its ordinary result allocation is
funded. A new public wrapper is not justified by these unresolved facts.

Exact node observation could use an admitted observation plus entity, select the
Head lineage association from that held root, then demand the exact node page.
That would return semantic LineageNode without exposing roots/cells/counters.
Need prove whether the same actual node basis is used by all reviewed class3
concurrent/custody controls, not infer equivalence from matching IDs.

The cfg(test) graph/divergence methods eagerly collect vectors/sets. Promoting
those full collectors would need an owner funding/capability design; they are
not minimal read-only observers. Their private subcases need an explicit C2
restore reference when splitting the public matrix.
