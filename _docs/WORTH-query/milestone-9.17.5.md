# Milestone 9.17.5: Branch-Scoped Application Program Evolution

> **Status:** Planned successor to [9.17.4](./milestone-9.17.4.md).
> Static graph authoring and ordinary consumer migration must already work.
> This milestone adds program evolution across exact composite branches.
> [9.17.6](./milestone-9.17.6.md) then adds runtime-authored workflow instances.

## Goal, Entry And Completion

Permit two product branches to retain different supported application programs,
adopt a new program on one branch without changing its sibling, and preserve
exact interpretation, current authority and all performed-effect custody.
Semantic revision is branch/composite meaning, not one process-global latest flag.

Consume 9.17.4's canonical composition, typed feature/operation/output/rule contracts,
installed providers, exact source expectations, completed candidate validation,
performed-publication delivery, managed resources and migrated consumers.
The compiler-enforced handoff contract in 9.17.4 remains normative here, including
private constructors, no string/raw-ID substitutes and no weaker ordinary entry.

Closure requires branch-local compatible adoption, incompatible state migration,
exact stale/failure outcomes, sibling independence, retained interpretation,
existing continuation disposition and explicitly broader adoption with honest
partial progress. The first phase reaches a real P0 -> P1 adoption and post-adoption
mutation/readback before expanding diff or migration coverage.

Do not implement multi-parent merge, rebase, dynamic user-authored workflows,
arbitrary code loading or a general schema-migration framework. Existing fixed
workflows/conditional operations and their recovery are real consumers here.
9.17.6 adds dynamic definition/instance disposition at the owner seam established
here, rather than making this milestone wait for its workflow product.

## Decisive Production Journey

Use the actual CAD composition and command/read endpoint certified by 9.17.4.
P0/P1 are separately compiled validated definitions supported by the same host
provider contracts. A small public cross-crate graph consumer proves the same
platform behavior without depending on private CAD.

1. Install P0. Create lawful geometry; retain its composite occurrence. Fork A/B.
   Keep an admitted operation, a page/live interest and pending producer on A.
2. Change source geometry on A while retaining its exact Signal basis and P0
   interpretation. Observe expected coordinates/volume independently.
3. On B prepare and publish P1: change a declared computation/rule contract through
   actual installed owner definition work, not just a revision label. Perform a
   post-adoption source edit and observe output that distinguishes P1 from P0.
4. A remains callable under P0 with fresh authority and can complete its parked work.
   Its retained result remains exact; no process-global generation invalidates it.
   B's pre-adoption candidate cannot publish after P1 activation.
5. Pair the correct visible ID with foreign A/B component/lowering/program evidence.
   Deny affinity substitution before effect. Include a valid twin reaching publication.
6. Race two preparations on B against the same head. One adoption performs; the
   other returns stale without changing activation. The next ordinary call sees the
   performed program and exact component bases, never a mixed combination.
7. Lose composite publication after owner definition preparation. The owner effect
   has real custody but P1 is not active on B. Resume exact cleanup/publication
   recovery; do not update a Query registry to turn the loser into installed meaning.
8. Tighten a rule over incompatible state. Deny without effects. Supply a real bounded
   migration candidate, validate the resulting owner state under P1, and adopt on its
   exact source. If source moves, reject stale migration; do not rerun the rewrite.
9. Revoke permission independently. Retained P0 interpretation is not authority.
   Mandatory cleanup after a performed effect remains reachable through its owner.
10. Close readers, pending interests, old program support and branches in legal order.
    Outstanding exact-effect custody blocks disposal rather than being leaked or lost.

For an inexpensive exact oracle, a public model uses a declared bounded-dimension
rule and a derived numeric result whose P0/P1 formulas differ. CAD supplies the
production geometric endpoint. Both assert actual values, rule verdicts, component
bases, producer contacts and performed outcomes; a program digest changing is not
evidence that runtime interpretation changed.

### Explicit broader adoption

Use three independent branches A/B/C with one selected coverage token. Make C
incompatible: preflight denies before any adoption. Repair C, prepare again,
publish A and park before B. Move B's head and introduce another branch D.

A remains performed; B's prepared transition is stale; C is unperformed pending
work; D is outside the selected inventory. Return those exact dispositions and
retain required custody. Resume remaining work only after explicit fresh
preparation/coverage validation. Never call this an atomic multi-branch rollback
or silently extend the operation to D. Also test cancel before first effect,
cancel after A, exhausted preparation retention and owner-unpublished B.

The target order is explicitly selected by the caller, not identity sorting.
Order controls reporting/progression, not precedence of semantic conflict resolution.
Reuse ordinary per-branch publication and lifecycle machinery.

### Existing fixed workflow and delivery custody

Prepare an existing Bank approval/conditional continuation, an unpublished outbox
and retained publication interest under P0. A proposal to remove a required operation
must inventory those consumers and reject missing dispositions before activation.
Compatible continuation carriage obtains current admission; incompatible continuation
retires/cancels while performed external/provider obligations remain recoverable.
Late performed-change delivery retains its original occurrence/program meaning.
Do not replay the business effect or relabel approval to P1.

This tests existing fixed workflow custody. User-authored revision A/B and running
dynamic-instance migration are added by 9.17.6 using this same adoption mechanism.

## Product Decisions

### Composite occurrence and branch-scoped adoption

One canonical program governs each selected composite occurrence. Different branches
may concurrently use different supported program revisions. One semantic root means
one unambiguous composition for that occurrence, not one process-global latest meaning.

Keep host/provider compatibility and lifecycle identity, current principal/security
admission, and branch semantic activation distinct. A branch's program revision is
bound to owner-issued Relational and Signal bases and the corresponding admitted Bridge
installation evidence carried through World selection/publication. A program digest or
Query-side revision counter cannot replace these witnesses. Do not create a parallel
version tuple, history head or branch-to-latest-program authority registry.

An installed immutable program may be shared only under validated contract equivalence;
requests resolve the program associated with their exact selected composite occurrence.
Historical reads use that occurrence's interpretation under fresh security and supported
host contracts. Retaining data/program meaning never freezes permission. Compiled program
lookup is bounded by selected identity; ordinary requests do not scan all branches.

Query installation compiles program support and compatibility. Query execution's
product-operation owner coordinates adoption; World performed publication carries
the branch activation truth. Installation owns no mutable branch-current table.

Adoption defaults to one explicit branch. It validates old/new program meaning, state,
workflow/recovery dispositions, exact target reference/incarnation/head and component
bases, then advances only that branch through existing owner preparation and performed
World publication. Unchanged components retain exact bases without mutation. Signal
changes are authoritative definition successors with matching Bridge evidence, not
ordinary evaluation or registry edits. A failed World publication leaves retained owner
effects and exact recovery, never an activated Query product program. Existing
correspondence compatibility/rebind denials remain; adoption cannot synthesize missing
Bridge authority or bypass a required owner rebind.

Semantic diff includes facts, rule owners/scopes, ports, suppliers, workflow vocabulary
and effect posture, classifying unchanged/additive/restricting/meaning-changing/migration
requirements. Unsupported host/provider contracts deny before effects. Reuse requires
validated equivalence. Preparation fences the actual target head/component/program
basis through publication; source-local ordinary edits retain their existing weaker,
accurate source footprint rather than inheriting a global head comparison.

Old candidates on the adopted branch cannot publish after activation. Affected page/live
continuations close with semantic-revision-changed; lawful retained history remains
readable through fresh admission. An unchanged sibling's admissions, interests and
supported program remain valid. Global security revocation is still freshly enforced.
Running workflows in scope require compatible carriage, migration or cancellation;
carriage uses that branch's admitted current contracts. Every performed obligation has
satisfied, carried or exact-occurrence recovery disposition; missing disposition denies.

Application-wide adoption is an explicit broader operation, not a hidden consequence
of local adoption. It preflights exact owner-issued branch coverage and every branch's
state/custody. Incompatible covered state denies before effects. It then uses existing
per-branch publication contracts and reports performed/unchanged/pending outcomes with
exact recovery; it cannot claim unsupported atomic multi-branch publication. Coverage or
head movement invalidates remaining prepared work, never silently expands scope or
rewinds branches already advanced. Ship bounded progression and its partial-effect
proof, not a generic migration engine or new transaction runtime.


### Three identities that cannot be collapsed

| Identity or product | Owner and meaning | What it cannot establish |
| --- | --- | --- |
| Canonical program revision | Query declaration; stable content/contract identity | Which branch currently uses it, current permission or host availability |
| Installed support binding | Existing installation owners; exact native schema, provider implementations, codecs and supported program contracts | A branch activation, a World publication or an implicit global upgrade |
| Branch program activation | Owner-admitted installation/definition evidence consumed through performed World publication | Another branch's meaning, authority for later requests or completion of external effects |

The selected occurrence determines effective program interpretation through carried
owner evidence. Query may retain bounded immutable lookup/cache entries keyed by that
evidence, but a mutable branch-to-latest-program table is not authoritative.
Program retirement removes support only after current branches, retained
interpretation and mandatory custody have lawful disposition. Capacity exhaustion
denies new support admission; it cannot evict a program still needed by an admitted
read or recovery obligation.

A host may support P0 and P1 simultaneously. Support comes from explicitly installed
compatible native contracts and concrete implementations, not runtime loading of
arbitrary Rust or untyped schema merging. An added feature needing unsupported types,
providers or root correspondence returns a typed support/rebind requirement before
effects. The minimal P0/P1 proof uses already-supported contracts. Do not pretend
unsupported rebind can be satisfied by refreshing a generation counter.

### Semantic diff is input to admission

ApplicationSemanticDiff compares canonical authored meaning, not generated file text.
It includes qualified feature/composition identity, facts/ownership, ports and scope
bindings, rule owner/scope/applicability, lifecycle transitions/authority, output
grammar/lineage, materialization strategy, publication and effect/resource posture.
Stable identities survive Rust renames. Removing an owned fact is different from
removing a reader; tightening a rule is different from changing diagnostics.

The diff returns typed change categories and concrete validation/migration requirements.
Its report grants no write or migration authority. Each requirement identifies the
affected installed contract and scope, the expected source/program basis and the
validation or rewrite needed; it is not a caller-supplied boolean exemption.
Unchanged paths carry validated semantic equivalence, including dependent contracts.
A changed invariant implementation must change its declared contract/version;
opaque code equality cannot establish semantic equivalence.

### Exact preparation and effects

| Phase product | Constructed by | Required contents and next consumer |
| --- | --- | --- |
| Validated target program | 9.17.4 declaration validation | Canonical target and structural/provider requirements; support admission only |
| Admitted program support | Installation owner | Exact native/handler/codec compatibility and bounded retention; branch preparation |
| Prepared branch adoption | Query execution over owner-issued target observation | Branch/incarnation/head, component and Bridge evidence, source/target program, state validation, reservations, migration and custody dispositions; owner publication |
| Prepared migration candidate | Existing bounded reader/writer and actual invariant owners | Exact tracked source, permitted rewrite, complete proposed state under target rules; same adoption publication |
| Performed adoption | Terminal consuming World Performed | Actual new occurrence/component bases and target interpretation; new requests and delivery |
| Unpublished adoption | Existing World/provider recovery owner | Performed owner effects plus original source/target and cleanup/publication obligation; exact recovery only |

These semantic products reuse concrete owner/proof types; do not wrap a report in
a public marker to manufacture readiness. Constructors are private at the responsible
boundary. Preparation is consumed by publication; no raw draft or target revision
alone can reach the effectful entry. Static types prevent omission; live equality and
support/currentness are checked at owner boundaries.

The first expensive traversal begins only after identity/support/current authority
and declared resource ceilings are admitted. Prepare computes the affected scope,
gathers required current data and checks actual proposed state. It reserves candidate,
definition, validation and custody resources before effect construction. Foreign
migration candidates or smaller-than-required reported footprints deny.

The adoption plan fixes per-component disposition: retain exact basis, prepare an
owner successor, or return the owner's explicit unsupported/rebind requirement.
Relational migration and Signal definition change, when both required, enter one
supported coordinated composite publication. A separate visible data migration
followed later by a program switch cannot claim atomic adoption. Intermediate drafts
may exist as noncurrent candidates, never an unvalidated public world.

World comparison remains the linearization point. No current-program cache, provider
callback, owner-local definition success or diagnostic receipt activates the target.
On publication conflict, preserve any already-performed owner effects with the
unpublished terminal. On successful publication, use 9.17.4's typed delivery return
path to reconcile required materializations; source/program success does not imply
derived completion.

### Denial and recovery semantics

| Condition | Required outcome and effect posture |
| --- | --- |
| Foreign target/source/program/provider evidence | Typed affinity/support denial before effects |
| Required implementation/correspondence unsupported | Typed unsupported/rebind requirement; no fabricated compatibility |
| Target rules reject existing state | Migration-required or invariant denial with named violated scope |
| Missing continuation/recovery disposition | Adoption denied; old program remains active |
| Target head/component/activation moved | Stale preparation; no silent rebase or proof retagging |
| Resources exhausted before owner effects | No publication; release temporary reservations |
| Owner effects occurred but World did not perform | Exact ProductUnpublished custody; no branch activation |
| World performed, subsequent delivery/settlement interrupted | Performed adoption plus bounded pending obligation |
| Same idempotency key and same adoption intent | Existing performed result/recovery without repeating migration or definition effects |
| Same key with changed target/program/coverage/migration intent | Typed conflict, never replaying a different adoption |

Cancellation before effects releases preparation. Cancellation afterward states which
owner effects/publications happened and transfers exact recovery. Removal of caller
capability cannot strand mandatory owner cleanup. Recovery actions cannot widen the
migration or revive removed ordinary APIs.

Existing concrete outcome families remain canonical. New detail types distinguish
program support, state migration and branch coverage only where they add meaning;
they do not flatten ordinary publication outcomes into a second success enum.

### Resource, continuation and support dispositions

For every live object affected by local adoption, preparation must derive one lawful
disposition from its owning contract:

- Mutable prepared attempts cannot publish with obsolete target activation.
- Page/live continuation closes with semantic-revision-changed and fresh readmission.
- Retained observations preserve their exact source interpretation under current
  disclosure; they do not become current state or mutation authority.
- A compatible managed continuation is rebound only by its existing readmission owner
  with current authority, source/definition compatibility and new execution evidence.
- Incompatible uneffected work cancels/retires through its owner.
- Performed outbox/provider/settlement work remains exact-occurrence recovery even
  when its ordinary operation is no longer available.
- Pending derived delivery either proceeds under valid exact old observation or
  returns explicit superseded/reconciliation posture; it never runs under accidental P1.

These checks cover the selected branch, not all branches sharing a support entry.
Broader host removal is a separate explicit support-retirement operation that must
inventory every actual user; it cannot hide inside branch-local adoption.

## Required Public Experience

These are target Rust call shapes to compile through the host facade when shipped.
Identity and proof are supplied by owners; names below do not authorize alternate
constructors or expose raw World commits to ordinary callers.

~~~rust,ignore
let request = application.request(&principal, &scope).on_branch(target_branch);
let proposed = RevisedCadApplication::validated_program()?;
let impact = request.programs().compare(&proposed)?; // descriptive diff
let prepared = request.programs()
    .adopt(proposed)
    .requirements(impact.requirements())
    .migration(migration_input)
    .idempotency(adoption_key)
    .controls(adoption_limits)
    .prepare()?;
let outcome = prepared.publish();
// Match Performed vs NoEffect/denial vs exact unpublished/recovery custody.
// New requests resolve the actual published program for their selected branch.
~~~

Requirements are owner-checked obligations, not a report reclassified as a permit.
A no-migration adoption uses a validated unchanged/compatible-state result from the
same preparation, not an empty proof. The migration input names a declared operation
and its typed inputs; the owner executes its bounded preparation against the selected
source rather than accepting arbitrary prevalidated data.

For broader scope, an explicit on_branches(owner_issued_coverage, ordered_targets)
entry returns a managed adoption handle. Its progress names exact per-branch
performed, unchanged, stale, pending and recovery results. Advancing it uses fresh
admission and exact prepared evidence; close cannot discard unsettled owner effects.

Inspection reports selected branch, source/target program, component retain/change
posture, incompatible state, custody dispositions and next legal action. It never
exposes a hidden global current-program switch or protected data without disclosure.

## Acceptance And Verification

The P0/P1 journey must prove different actual interpretation, not merely different
digests. Performed publication is the only activation fact. Retained/later requests,
pending producers, exact output reconstruction and current security all use the
proper selected program and component bases. Unaffected branches keep progressing.

The broader sequence must demonstrate truthful partial progress and no rollback
fiction. Every migration/continuation/support resource has an owner through denial,
cancellation, owner-unpublished, performed and close. Required effect custody survives
capability loss. A source/program mismatch must not be repaired by casting a token,
rebuilding an ID or invoking an ordinary operation again.

Measure work by target branches, affected contract/state scope, validation visits,
owner component contacts, retained program/resource bytes and publications. Local
adoption must not scan every sibling; broad adoption pays for its explicit inventory.
Retained interpretation may pay for bounded supported versions; eviction cannot erase
correctness. Unchanged components have zero mutation contacts. No canonicalization
or whole-program diff per ordinary request.

Use 9.17.4's compiler/facade/codec requirements and the repository test-requirements.
Focused owner and real consumer evidence runs first; reuse unaffected compiled tests.
Before boundary-relevant phase closure run boundary-check, agent-context check,
scoped formatting, dirty line-cap guard, warning-free required builds and the affected
World/Signal/Query/product tests. Exact command forms remain:

~~~text
cargo run --manifest-path tools/boundary-check/Cargo.toml -- --root .
cargo run --manifest-path tools/agent-context/Cargo.toml -- check
scripts/ci/check_workspace_rust_line_caps.sh dirty
~~~

Review asks whether a current branch can acquire another branch's program, whether
a pre-CAS owner result activates anything, whether missing preparation compiles,
and whether cleanup can lose an effect. No ledgers, recursive proof systems,
warning suppression or full rerun after immaterial edits.

### Future merge handoff

[Cross-runtime merging and branching](../cross-runtime/merging-and-branching-roadmap.md)
owns merge/rebase, multi-parent publication and conflict resolution. This milestone
adds no merge executor, placeholder parent vectors or second conflict authority.
It must preserve portable identities and versioned composition, rule owner/scope,
dependency/output, lineage, workflow-definition and effect-posture meaning so those
owners can reconcile actual semantics rather than flattened values.

The successor must select exact source/target composite occurrences, establish the
resulting program meaning, and validate the combined owner candidate under its rules.
Two independently valid branches do not prove a valid combination: a wider opening
and a weaker supporting header can conflict even when each branch passes separately.
Parent assessments/approvals cannot substitute for resulting-world evidence. Derived
output is reused only under owner-validated dependency equivalence; affected results
otherwise recompute. Workflow progress and external effects retain exact provenance
and recovery, not duplicated execution when records combine. These are preserved
handoff constraints, not claims that this milestone certifies future merge behavior.
